# IDEAL — Audit and implementation record (2026-11-24)

## Status of the requested specification

The task referenced `docs/IDEAL_MASTER_BUILD_SPEC.md` as the main product and engineering
specification. **That file does not exist in this repository**: it is absent from the working
tree, from every local branch, and from the full commit history (`git log --all --
'*MASTER*' '*SPEC*'` returns nothing, and no branch contains a matching path).

Because of that, this pass could not be scoped against the specification's own definition of
"missing feature". What was done instead is the part of the request that is verifiable without
it: a source-level audit of what works, what is incomplete and what is missing, followed by
fixing the concrete defects and dead-ends the audit found, with automated tests covering them.

Re-adding the specification is the only blocker for the remaining feature work.

## Method

1. Read the server, database, authentication/permission layer and every page under `src/`.
2. Extracted all 141 API endpoints from `server/routes.ts` and all UI call sites from `src/`,
   then compared them to find capabilities that no button reaches, and buttons that call
   nothing.
3. Ran the existing automated suites (TypeScript, French-only UI check, data protection,
   lifecycle, business simulation, production build).
4. Ran the real interface in a browser (first-run setup, project detail, tax page, expense
   list, treasury journal) and asserted the resulting database state through the API.

## What already worked (verified, not rebuilt)

- First-run setup, login with rate limiting and audit trail, session tokens, 5 roles with
  server-side permission checks on every route.
- Clients, projects, phases/tasks, change orders, commercial documents (devis, proforma,
  bon de livraison, facture, avoir), payments with duplicate protection and reversal,
  purchases and supplier payments, stock movements, vehicles, fuel, repairs, maintenance,
  tools, attendance, payroll periods and payslips, documents, reports and XLSX exports.
- Lifecycle rules: 7-day deletion window, dependency blocking, archive/restore, annual
  retention review with notifications.
- Backups: verified ZIP creation/restore with SHA-256 checks and a pre-restore safety copy.
- Interface is French-only; SQLite + Express + Electron, loopback only, no cloud service.

## Defects found and fixed

| # | Defect | Impact | Fix |
|---|---|---|---|
| 1 | Cancelled expenses were still summed by `calculateProjectFinancials`, the dashboard `totalCosts` KPI and the fiscal summary (`/taxes/summary`). | After cancelling an expense, project cost, dashboard costs and estimated profit/IBS stayed inflated, while the treasury had already been counter-passed. Contradictory figures between treasury and reporting. | All three aggregates now exclude `status = 'cancelled'`. Covered by `test:regressions`. |
| 2 | Tax rules could only have their rate edited: the `tax_rules` table was never seeded and there was no create endpoint or button. | The "Comptabilité & Impôts" configuration table was permanently empty and non-configurable. | Added `POST /taxes/rules` with validation, extended `PUT /taxes/rules/:id` (name, rate, effective date, status, notes) and added a creation dialog plus archive/reactivate action. |
| 3 | Tax rule date validation accepted impossible dates. | `2026-02-31` was silently accepted and rolled over to March by `Date.parse`. | `isValidIsoDate` now re-serialises the parsed date and rejects any rollover. Covered by `test:regressions`. |
| 4 | Project API supported creating phases and contracts and recording milestone receipts, but the project tabs were read-only dead ends. | Users could see "Contrats & Jalons" and "Phases & Tâches" but could never populate them from the interface. | Added "Nouvelle phase", "Nouveau contrat" (with retention rate and a milestone editor) and an "Encaisser" action per milestone. |
| 5 | Expense cancellation and treasury counter-passing existed in the API with permission checks, but no button invoked them. | Historical corrections required direct API access; the visible journal had no way to undo an entry. | Added "Annuler" on expenses and "Contre-passer" on treasury rows, with `window.confirm` (the project's existing convention) and `lifecycle:cancel` / `lifecycle:reverse` permission gating. |
| 6 | `pattern="[A-Za-z0-9._-]+"` (setup) and `pattern="[A-Za-z0-9][A-Za-z0-9_-]{1,29}"` (services) are invalid under the modern `v` regular-expression flag. | Browsers threw a `SyntaxError` and **silently ignored** the client-side username/code validation. | Escaped the hyphen (`\-`). Verified valid under `RegExp(..., 'v')` and confirmed no console error remains. |

## Tests

New suite: `scripts/test-regressions.ts` (`npm run test:regressions`), also added to both
GitHub Actions workflows after the simulation step. It runs against an isolated temporary
database on an ephemeral port and asserts, through HTTP:

- tax rule create / uppercase normalisation / list / rate update / archive / reactivate;
- rejection of invalid code, rate above 100 and impossible dates;
- phase creation and rejection of an empty name;
- contract creation with retention computation, milestone storage, partial then paid status;
- cancelled expense leaves project cost, dashboard cost and cash balance net at zero, and
  stays visible in history with `status = 'cancelled'`;
- treasury reversal nets the balance to zero, blocks a second reversal and keeps the original
  row flagged `reversed`;
- role permissions: a driver cannot create tax rules or read fiscal data, a storekeeper cannot
  delete clients or cancel expenses.

## Known gaps deliberately left open

- **Tax rates are not seeded.** Legal rates must be confirmed by an Algerian accountant, so the
  application ships an explicit empty state and lets the user enter validated values; it does
  not invent TVA/CNAS/IRG/IBS/TAP values.
- `updated_at` is backfilled by migration 5 for existing rows, but new inserts in some tables
  still store an empty value; it is not displayed in the interface.
- `POST /lifecycle/notifications/sync` is reachable but not called from the UI (the server also
  runs the sync hourly).
- A `/favicon.ico` request returns 404; cosmetic only.
- Local Playwright cannot launch in this Linux sandbox (missing `libnspr4` and no root to
  install it), so the committed `e2e/` suite was not executed here. The interface was verified
  with the cloud browser instead.
- Windows installer/AppX packaging was not run (requires a Windows runner).

## Constraints respected

Lightweight offline Windows architecture, French-only interface, SQLite storage, loopback-only
server, no paid service and no mandatory cloud dependency were all preserved. No existing
feature was rewritten, no table or column was dropped, and no user data was deleted; the only
schema-adjacent change is the `POST /taxes/rules` endpoint and stricter validation.
